list 慢的原因，是每次运行都在重复一些本来可以不做的事。

**机器空闲时，`obit list` 的 p95 从 191、183、178、179、267 毫秒降到 84、86、80、90、139 毫秒（单跑和 2、4、8、16 个并发）。**

这是 11 月 23 日晚上到 24 日中午的工作，接着上一篇：常驻单写者让 hook 过了门槛，同期的 `obit list` 却没过。

## 起点：hook 过了，list 没过

JSON 加常驻单写者那一版，16 个并发时单个 hook 的 p95 是 392.72 毫秒，整波 408.75 毫秒，都在门槛之内。同期的 `obit list` 是 357.09 毫秒，门槛是 250 毫秒。

测量分三个时间窗，每窗 21 波，list 的 p95 是 370.46、295.95 和 252.19 毫秒，三窗都没过。同一轮里 main 作基线是 347.49 毫秒，新版比它还高 9.60 毫秒。

我们另做过一次对照：16 个不触发写入和 Git 的 PreToolUse 加上同样的 `obit list`，p95 仍然有 215.11 毫秒。这提示进程启动和调度的争用本身就很重，但那次对照没有在同一波里只切换一个变量，所以剩下的差值不能直接归给启动或存储。

下一步就是分段量。

## 分段测量：多出来的时间在 main 之前和 JSON 解码

16 个 hook 同时跑时，list 多花的时间集中在两处：进入 Go 的 `main` 之前，和热账本 JSON 的解码。

我们在 list 里加了探针，对比单跑和 16 个并发下每一段花多少。带探针的调用里，中位数的变化是：

| 段 | 单跑 | 16 个并发 |
|---|---:|---:|
| 进入 `main` 之前 | 41.70 毫秒 | 80.97 毫秒 |
| 热账本 JSON 解码 | 19.59 毫秒 | 44.84 毫秒 |
| 读两份文件 | | 合计 2.22 毫秒 |
| 表格处理 | | 1.34 毫秒 |
| 真正写标准输出 | | 0.46 毫秒 |

**写输出只占 0.46 毫秒，输出管道不是慢的地方。**

同一个版本，同样的测法，换一个时段重新量，无探针的 16 个并发 list p95 是 249.24 毫秒，比之前三窗的 357.09 毫秒低得多，离门槛只差 0.76 毫秒。同一份代码，换个时段量，p95 就差了 100 多毫秒，所以后面的每一步都用同机交错、逐对相减来比。

### 其中一段有名字：Cobra 的双击判断

Windows 上，Cobra 在解析命令之前会调用 `mousetrap.StartedByExplorer()`，查父进程是不是资源管理器，用来决定要不要显示双击提示并退出。查父进程要把系统的进程快照枚举两遍：`syscall.Getppid` 一遍，mousetrap 查父进程名一遍。

这个函数单跑要 24.17 毫秒（中位数），16 个并发时 33.80 毫秒，占"根命令建好到进入 `list`"那段时间的 99.6%。

## 先试"跳过这个检查"：单跑稳赚，16 个并发的 p95 不降反升

只对字面量 `list` 跳过双击判断，是一个很便宜的实验，我们做了 84 对的配对对照（A 是原版，B 是跳过检查）。

| 场景 | 对数 | A 中位 / p95 | B 中位 / p95 | 超过 250 毫秒的次数 A / B | B 更快 |
|---|---:|---:|---:|---:|---:|
| 单跑 | 42 | 139.74 / 172.41 毫秒 | 116.70 / 128.84 毫秒 | 0 / 0 | 42 / 42 |
| 16 个并发 | 42 | 254.71 / 305.34 毫秒 | 236.39 / 355.41 毫秒 | 25 / 9 | 31 / 42 |

单跑每一对都更快，逐对中位数省 25.68 毫秒。16 个并发时 31 对更快，超过 250 毫秒的次数从 25 次降到 9 次，**但最慢的几次拖高了 p95，从 305.34 升到 355.41 毫秒。**

跳过检查可以当作日常提速的候选，对压低 16 个并发的 p95 没有用。

## 16 个并发是不是太极端：把验收改成按 2 到 4 个算

16 个 hook 几乎同时启动，是我们刻意造的压力场景。开着 16 个工作区，并不等于 16 个 hook 同时发。

我们没有量过日常实际会有几个 hook 重叠，估计是 2 到 4 个。所以 list 的验收口径改成：

**按 2 到 4 个 hook 并发来算，p95 门槛仍然是 250 毫秒；16 个并发照测，只当峰值参考。**

原来的数字门槛一个没有放宽，只是换了一个更接近日常的负载来量。

## 四个方向各试一遍，每个都测单跑和 2、4、8、16 个并发

我们把能想到的四个方向各做了一个构建，在同一次交错运行里一起量：

| 方向 | 做了什么 | 16 个并发 p95 |
|---|---|---:|
| a1 跳过双击判断（上面那个对照） | 只对字面量 `list` 关掉 Cobra 的检查 | 852 毫秒 |
| a2 便宜的双击判断 | 向内核问父进程的映像名，确定不是 `explorer.exe` 才关掉 Cobra 的检查 | 887 毫秒 |
| b 常驻进程代为打印 | list 向常驻进程发请求，原样写出返回的字节 | 362 毫秒 |
| c 缩短进程启动前的开销 | 查证后没有可删的 | 不变 |
| d 解码这一段 | 摘要投影装得下真实的墓地记录，常驻进程保留已核对的快照解析，内存上限不再低于一次解码 | 737 毫秒（只含摘要投影的修复） |
| 全部合起来 | a2 + b + d | 329 毫秒 |

这一次交错运行时机器被另一个进程拖着（全盘扫描），所以绝对值偏高，只能看同一次运行里的相对关系。基线在同一次运行里是 833 毫秒。

读这张表：a1 和 a2 单独做，对 16 个并发的 p95 几乎没有帮助；b 一个就把它从 833 降到 362 毫秒，效果最大；三个合起来是 329 毫秒。

## 五个根因，按对 list 的影响排序

### 1. 每次 list 都付一次双击判断

单跑约 24 毫秒，竞争时更多。`obit --version` 在同一台机器上从 68.6 毫秒降到 42.2 毫秒，裸 Go 程序是 31.3 毫秒，差值就是这一项。

现在的做法是向内核问一下父进程的映像名，确定不是 `explorer.exe` 才关掉 Cobra 的检查，其他情况 Cobra 照旧判断。所有命令都省了这笔，无参数双击的行为不变。

测试把测试二进制复制成 `explorer.exe`、`Explorer.EXE`、`explorer.exe.bak.exe` 和 `notexplorer.exe` 当父进程，只有前两个保留 Cobra 的提示。把判断临时改成总是跳过，测试失败。

### 2. list 在每个新进程里重做常驻进程已经做过的事

打开服务、读 `store.json`、解码、核对墓地快照，这几段加起来约 30 毫秒，竞争时翻倍。常驻进程本来就持有账本，也有一个只认当前用户的本地端点，所以让它代为打印。

没有常驻进程、常驻是旧版、请求被拒绝、超时、返回空，都退回 list 自己读账本。输出和原来逐字节一致。

### 3. 常驻进程固定 12 MiB 的内存上限，比一次解码的工作集还小

**解码 1000 条活动加 1000 条墓地记录产生的垃圾放不进上限，回收器就一直在跑，同一次解码从 3 到 5 毫秒变成 6 到 16 毫秒，墓地摘要从 7 到 9 毫秒变成 18 到 39 毫秒。**

只改这个上限，真实形态账本、4 个并发下 list 的 p95 从 111.6 毫秒降到 80.1 毫秒。上限现在随 `store.json` 的大小变：64 倍，最低 32 MiB，最高 512 MiB，启动时和每一步都重新核对。

### 4. 摘要读取的投影，装不下命令行写下的墓地记录

这是这一轮最意外的发现：**真实的账本从来走不到摘要读取的快路径。**

快路径用严格的解码，遇到 `longNames`、`parentRef`、`operationRef`、`originRef`，或 `parentChains`、`operations`、`origins` 三张表，就报"未知字段"，退到整本冷快照的完整解码。`obit bury` 写下的每一条墓地记录都带这些字段。前几轮测试用的种子账本只有最少的字段，恰好绕开了它，门槛场景因此低估了真实用户的耗时。

现在的投影接受这些字段，并检查每个引用都落在表里的一行上。表的内容不再解析，因为快照字节的哈希已经证明它们就是提交的那一份。没有常驻进程时的 list、统计和窗口摘要也因此受益，单跑 p50 从 139.4 降到 123.3 毫秒。

### 5. 不能删的部分：操作系统建进程

裸 Go 程序从创建进程到 `main`，单跑、4 个并发和 16 个并发下是 28.4、29.5、39.4 毫秒。`obit` 是 35.6、38.6、50.9 毫秒。差出来的 7 到 12 毫秒才是我们的，其中包初始化约 5 到 6 毫秒，最大一项是 `net` 的 `WSAStartup`，3.1 到 4.8 毫秒。

`net` 被 cobra 的 pflag、go-winio 和 MCP SDK 各自引入，要拆掉就得放弃它们或拆成两个二进制。我们还试了只保留 list 和 hook 的精简二进制（12 MB），包初始化同样是 4.7 到 7.2 毫秒，拆命令也省不了多少。**这一段没有值得删的初始化。**

## 最终数字：2 到 4 个并发和 16 个并发都在 250 毫秒以内

机器空闲、每档每个构建 42 波、真实形态的账本时，最终版在验收口径下达标，16 个并发的峰值参考也达标。

| 并发 | 改造前 p50 / p95 | 最终版 p50 / p95 | 超过 250 毫秒的次数 |
|---|---:|---:|---:|
| 单跑 | 166.2 / 191.4 毫秒 | 72.2 / 84.2 毫秒 | 0 / 0 |
| 2（验收） | 158.1 / 182.6 毫秒 | 72.3 / 86.1 毫秒 | 0 / 0 |
| 4（验收） | 155.3 / 177.9 毫秒 | 67.8 / 80.1 毫秒 | 0 / 0 |
| 8 | 164.3 / 178.9 毫秒 | 76.9 / 89.9 毫秒 | 1 / 0 |
| 16（峰值参考） | 229.1 / 266.7 毫秒 | 97.2 / 139.0 毫秒 | 9 / 0 |

一万条活动加一万条墓地（12 波，p95 就是最大值，只报数字）：单跑从 414.5 / 429.0 降到 124.5 / 225.9 毫秒，4 个并发从 421.9 / 449.0 降到 135.3 / 241.7 毫秒。

### 机器忙的时候没有全过

另一次测量时，机器上有一个进程在全盘扫描，整机 CPU 中位数在 2、4、8、16 个并发下分别是 51%、63%、71%、84%。这时最终版 2 个并发的 p95 是 219.5 毫秒，4 个并发是 222.0 毫秒，仍在 250 毫秒之内，原来是 401.5 和 508.3 毫秒，4 个并发有 20 次超过 250 毫秒。

**16 个并发是 328.9 毫秒，没有过峰值参考线**，原来是 833.0 毫秒。

## 行为和代价

- **输出逐字节一致。** 同一份账本、常驻进程在和不在两种状态下，`obit list`、`--json`、`OBIT_LANG=zh-CN`、`ls` 和 `list extra`（报错）在各个构建之间，stdout、stderr 和退出码全部相同。
- **协议是加性的。** 版本号仍是 1。旧版常驻进程把 list 请求当作无效请求拒绝，新命令于是退回自己读账本，有测试。
- **hook 没有变慢。** 机器安静时，最终版对基线的单个 hook p95：2 个并发 130 对 139，4 个并发 145 对 148，8 个并发 248 对 267，16 个并发 272 对 287 毫秒。
- **常驻进程多占约 10 MB。** 负载下工作集从 25 到 27 MB 变成 35 到 39 MB，私有字节从 56 到 58 MB 变成 65 到 69 MB，原因是内存上限的下限从 12 MiB 升到了 32 MiB。空闲时的占用没有单独量。
- **解码总是最新的提交。** 常驻进程对每个请求解码当时的 `store.json`，不保留旧副本，只有不可变的墓地快照在同一个哈希引用、同样的大小和修改时间下沿用上一次的解析。篡改快照的大小会被立刻拒绝，测试和变异检查都能抓到。

输出没有变化，只是更快，所以 README、官网和 `--help` 都不用改。

## 没做的和没验证的

- 只在 Windows 上量。list 请求在 Unix 套接字上走同一份代码，通过了交叉编译和 vet，没有在 Linux 和 macOS 真机上跑。
- 机器不是独占的，有一组数据里有外部的全盘扫描。p95 是 42 个样本里的第 40 项，不是总体的结论。
- "真实形态的账本"是探针合成的，字段取自实际 `obit bury` 写下的记录，不是从真人账本导出的。
- 全量 CI 还没跑。`internal/gui` 里有 4 个测试失败，在这次改动之前的 `24edcff` 上同样失败，和这次无关。
- 新构建的程序第一次运行明显更慢（裸程序首次从创建到 `main` 是 94 毫秒，后续约 13 毫秒，应该是系统的首次扫描），升级后的第一次调用会碰到。

改动在分支 `m3-json-resident` 上，最终提交是 `388788d`，没有合进 main，也没有发版。
