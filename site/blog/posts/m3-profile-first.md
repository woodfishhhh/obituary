同时开十几个 agent 的时候，讣告会变慢。11 月 22 日凌晨我们没有直接改代码，先把慢的地方量了一遍。

**1000 条活动加 1000 条墓地的账本上，16 个 hook 同时写，单个 hook 的 p95 是 1049 毫秒。**

## 16 个 hook 同时写：一秒多，同期的 list 也要将近半秒

并发越高越慢，到 16 个时已经远超一个 hook 该有的时间。

测量用的是真实的 `obit hook claude`（PostToolUse，已同意的项目）、真实的 Git 和真实的 NTFS 文件 ID，数据目录和配置目录都是临时的。每一波 k 个 hook 以 0、5、10、15 毫秒错开启动，65 毫秒之后再发一个真实的 `obit list`，每档 7 波。

| 并发 | 整波 p95 | 单个 hook p95 | 同期 list p95 |
|---|---:|---:|---:|
| 4 | 504 毫秒 | 438 毫秒 | 288 毫秒 |
| 8 | 584 毫秒 | 560 毫秒 | 228 毫秒 |
| 16 | 1272 毫秒 | 1049 毫秒 | 469 毫秒 |

16 个并发那一档共 112 次写入，其中 1 次在进程退出时还没登记，靠已有的队列重放补上，最终 112 条逐条对齐。

## 慢在哪：每个 hook 都整本读写账本，还自己去问 Git

时间花在进程启动、账本规模和排队上，单看哪一步都不算离谱。

最卡的是同时开 16 个 agent 的时候：**每个 hook 进程都要读写整本账本、自己去问 Git，互相排队。**

先看单个进程的底：

- 一个空的 Go 程序，从创建到退出，中位数 33.4 毫秒，p95 48.3 毫秒。
- 一个不碰账本的普通 PreToolUse hook，中位数 48.0 毫秒，p95 68.5 毫秒。
- 全部包的初始化加起来中位数 11.0 毫秒，其中 i18n 4.7 毫秒，net 3.7 毫秒。

再看账本本身，数字是中位数：

| 操作 | 1000 + 1000 条 | 10000 + 10000 条 |
|---|---:|---:|
| 读热账本 | 4.3 毫秒 | 35.9 毫秒 |
| 读完整快照 | 12.3 毫秒 | 111.4 毫秒 |
| 改一条记录的修订号 | 14.3 毫秒 | 82.2 毫秒 |

规模涨十倍，改一条记录的代价涨了将近六倍，因为每次提交都要把整本热账本重写一遍。

### 目录下葬会让读者干等

一万条记录时下葬一个目录，要逐项重新定位里面的每个条目。这段时间里，一个什么都不解码、只等共享锁的读者，6 次测量的中位数是 2043 毫秒，p95 是 2500 毫秒。1000 条时是 209 毫秒和 211 毫秒。

我们还单独量了不持锁的身份全扫描：1 个线程，一万个文件，中位数 1728 毫秒。所以等待不是加一棵路径树就能消掉的。

**放宽 hook 的超时，或者只换一个 JSON 库，都解决不了这个问题。**

## 定下来的方案：五批优化，每批一道数字闸门

先做能独立交付的，每一批都有同机配对的数字闸门，过不了就不合。

| 批 | 做什么 | 闸门 |
|---|---|---|
| A | 现有 JSON 上先做：hook 进程只加载自己那一支命令，词库用到才解析；list 只读需要的部分 | 普通 PreToolUse 的中位数至少少 4 毫秒，p95 不回退；一万条账本上 list 的 p95 从 376 毫秒向 300 毫秒以内靠 |
| B | 账本换成 SQLite，只改涉及的行，带可重放的回执 | 一万条账本上，持久连接改一行 p95 不超过 15 毫秒；单进程零散写不比 JSON 慢 |
| C | 常驻进程做唯一的写者，hook 只交观察，拿到持久回执就退出 | 见下 |
| D | 墓地和 doctor | 一万条记录下葬目录时，普通读者额外多等的时间 p95 小于 100 毫秒 |
| E | 有证据才做的零碎优化 | 同机配对收益至少 10% |

C 批的闸门是整个计划里最重要的一行：

**1000 + 1000 条账本、16 个并发的真实 hook：单个 hook p95 不超过 600 毫秒，整波不超过 800 毫秒，同期 `obit list` 不超过 250 毫秒。单个 hook 另设冲刺目标，300 毫秒以内。**

另外几条同一天定下的规矩：

- B 和 C 同一个版本发。B 可以先合进来而不启用，但不能单独发版，也不能迁移用户的账本。
- 目录下葬时逐项的身份复核一项不省。路径前缀只能用来筛选候选，不能据此跳过安全检查。
- C 的健康路径里，hook 不启动 Git，也不读写整本账本，拿到持久的接收回执就退出。"提前返回但没有持久接收"不算达标。
- B 要等 Docker 卷那项先合进主线，账本格式号取届时下一个没被占用的。

剖析里还做了一个 SQLite 的原型：一万行，Windows 命名管道，一个常驻进程握着连接。16 个客户端逐笔返回时每笔 p95 是 60.8 毫秒，加上 2 毫秒的合批窗口（一批最多 32 笔）之后是 8.8 毫秒。这组数字只覆盖存储这一段，不含启动 hook、Git 和提议，后面几轮实现的结果在另一篇里讲。

## A 批：不动账本格式，当天合进主线

A 批在 11 月 22 日 18:38 合进 main，没有引入 SQLite、额外的进程，也没有升级账本格式。

做了两件事：

- **hook 只注册自己的子命令。** 原来 `main.go` 在识别出这是 hook 之前，已经把所有命令都构造了一遍；`list` 和 `bury` 在注册时就去取本地化帮助、读配置；i18n 包在初始化时解析两份语言目录。现在词库用 `sync.OnceValue`，第一次用到才解析。
- **list 和摘要走只读的展示路径。** 冷快照的字节照样读取，哈希、归属、ID 和安全索引照样核对。遇到投影校验不了的证据、旧版账本或没做完的迁移，就退回完整读取。写入、复活、火化不用展示结果。

测量时旧版和新版都叫 `obit.exe`，AB 和 BA 交错，每组先跑两对预热，之后不剔除任何样本：

| 真实进程 | 配对数 | 旧 p50 | 新 p50 | 旧 p95 | 新 p95 |
|---|---:|---:|---:|---:|---:|
| 普通 PreToolUse | 61 | 53.13 毫秒 | 48.10 毫秒 | 60.03 毫秒 | 57.94 毫秒 |
| list，1 万活动 + 1 万墓地 | 35 | 372.20 毫秒 | 242.93 毫秒 | 427.87 毫秒 | 265.40 毫秒 |

两项都过了闸门，一万条账本上 list 的 p95 低于 300 毫秒。

### 闸门第一次没放行

中途的一个检查点上，list 的 p95 还有 567 毫秒，没有过 list 的闸门，hook 的 p95 已经从 63.21 降到 56.39 毫秒。当轮没有放行，改完再测，最终的 p95 是 265 毫秒。

### 测试先红：一个被判成健康的坏快照

把冷快照里的一个 `parentRef` 改成 -1 并重算哈希，展示读的投影当时仍然判它健康。补上引用范围检查之后，这个用例才转绿。

验证的另外几项：

- 44 个中英文场景的输出和旧版逐字一致，覆盖各级帮助、空列表和非空列表、JSON、`stats`、非法参数的退出码，以及 Claude 和 Codex 的普通命令与删除拒绝。
- 新增 3 个变异，都被预期的断言抓到。
- 手动触发的完整 CI（`full=true`）在 Windows、Linux、macOS 上全部通过。

A 批没有碰锁的排队，16 个并发的那几行数字还在。下一步是 B 和 C。
